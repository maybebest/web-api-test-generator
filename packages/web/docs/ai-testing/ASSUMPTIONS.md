# Implementation Assumptions

- The repository was empty at implementation time: no lockfile, no `package.json`, no existing Playwright setup, no application source, and no CI configuration were present.
- npm was selected because no `package-lock.json`, `pnpm-lock.yaml`, or `yarn.lock` existed.
- No existing Playwright installation was detected.
- The default target app is `http://localhost:3000` through `PLAYWRIGHT_TEST_BASE_URL`.
- A self-contained demo application lives under `demo-app/` (dependency-free Node http server). Playwright starts it via `webServer` whenever `PLAYWRIGHT_TEST_BASE_URL` points at a local host, so the committed login, checkout, recorded, smoke, and accessibility tests run for real with no external services. When the base URL is a remote environment, the app is assumed to be running there already and `webServer` is not started.
- No lint script existed at implementation time; CI and local validation use `npm run lint --if-present` so lint is enforced automatically if the team adds a lint script.
- Authentication setup is opt-in with `E2E_AUTH_ENABLED=true`; unauthenticated projects do not use `storageState` by default.
- Auth state is saved only after login success is asserted by selector or URL regex.
- The example-flow regression test runs against the demo app's `/ai-example/checkout` page and mocks `POST /api/orders` with the sentinel request ID `REQ-MOCKED-9999`. The live demo server always returns `REQ-1001`, so the assertion is falsifiable — it can only pass when the mock answered.
- The demo app can be started manually with `npm run demo:start` for discovery/exploration; `playwright test` starts it automatically via `webServer`.
- `.ai-runs/` contains local generation task artifacts and is ignored by git. It must never be committed or shipped in a distributed archive; `npm run ai:clean:check` fails when `.ai-runs/`, `playwright-report/`, traces, or videos contain real runtime files. Recursively empty directories and `.gitkeep`/`.DS_Store` placeholders are tolerated.
- Generated tests with spec headers are drift-checked against behavioral spec SHA-256 hashes. Editorial-only Notes changes are intentionally excluded from drift.
- Spec catalog output is generated into `docs/ai-testing/coverage.md` by `npm run ai:spec:catalog`. A regenerated copy is committed for traceability and CI also uploads it as an artifact; never hand-edit it.
- A spec marked `Generation Status | pending-generation` is human-reviewed but its test is generated later against a live environment; strict validation, `ai:test:gate:all`, and the UI runner skip its missing target test instead of failing. If the Target Test File already exists, the status is stale: strict validation and `ai:test:gate:all` fail with "Stale Generation Status".
- Auth-required generated tests are expected to run through `chromium-auth`; unauthenticated and optional-auth specs use browser projects derived from `Test Type`. Specs with `Auth | required` MUST name their Target Test File `<name>.authenticated.spec.ts` (a hard spec-validation error otherwise; non-auth specs must not use the suffix) — `chromium-auth` selects tests by `/.*\.authenticated\.spec\.ts/` and every non-auth browser project (chromium, firefox, webkit, mobile-chrome) ignores that pattern, so authenticated specs run only with storage state and never silently match zero tests.
- Test credentials are placeholders only. Real non-production credentials must come from local environment variables or CI secrets.
- Visual tests are opt-in through `ENABLE_VISUAL_TESTS=true` to avoid introducing flaky blocking CI checks before baselines are approved. They are additionally pinned to the `chromium` project (other browser projects `testIgnore` `tests/visual/`), and screenshot comparison policy is centralized in `playwright.config.ts` (`maxDiffPixelRatio` 0.01, animations disabled, baselines under `tests/__screenshots__/{testFilePath}/{projectName}-{platform}/`).
- Accessibility tests still depend on the configured base URL unless the team replaces them with app-specific stable mocks or a CI-served app.
- Page Objects use strict semantic locators (e.g. `this.page.getByRole('main')`); pages without a single landmark surface a strict-mode failure rather than silently fall through to `body`.
- Hand-written tests under `tests/regression`, `tests/smoke`, `tests/accessibility`, and `tests/visual` that are not bound to a spec must be listed in `tests/.no-header-allowlist`.
- Generated test gates copy failure evidence into the spec's matching `.ai-runs/<run>/evidence/` directory using `manifest.json` to identify the run; gates also typecheck via `tsc -p tsconfig.json` rather than synthesized flags.
- Raw manual docs are imported as `ai-draft` specs and require human review before the normal validation/generation gate can pass.
- Variant axes default to `Locale`, `Role`, and `Plan` and can be changed in `ai/config.json` before product-specific specs are authored.
- Business rules, human-readable data cases, and Data Cases as JSON are first-class spec sections, but the framework still relies on QA/product review to confirm domain semantics such as inclusive date calculations and channel-specific minimums.
- Minimum/duration rules require below-minimum, at-minimum, and above-minimum JSON data cases before reviewed validation passes.
- Default generation mode is single-test mode. Generate a suite only when the spec declares `Generation Mode | suite` or a suite is explicitly requested.
- Default generated-test execution target is Chromium only. Cross-browser generated-test execution is opt-in.
- The reviewer rejects XPath, `:nth-child` chains, unapproved raw CSS via locator ownership, direct generated-test `page.getBy*`/`page.locator(...)` calls outside Page Objects or Component Objects, combined-AC assertion step titles in suite mode, missing final assertion steps, assertions spread across multiple steps in one test, more than one primary `test(...)` block in single-test mode, undecorated negative cases in suite mode, stale declared mocks, missing JSON data case IDs, missing salient expected tokens, `test.use({ storageState })` literals, `test.skip`/`fixme`/`fail` in every form (defining-form and runtime calls inside test bodies), zero-argument `test()` calls, broad URL assertions, generic fallback visibility assertions, string-selector action APIs such as `page.click('css...')` (forbidden outright), and tautological `expect.poll(...)` assertions including producers that fold to a constant across multiple statements.
- The reviewer additionally enforces the single-mode `covered-ac-ids` annotation (annotation set == AC ids named in the primary test's step titles; every step title carries `AC-###` tokens), exact set-equality declaration of spec metadata `Tags` via the Playwright `{ tag: [...] }` option, and a fail-closed selector policy: unfoldable `.locator()` arguments and positional picks (`.first()`/`.last()`/`.nth(n)`) require a `// locator-policy:exception` comment. `.each` detection is AST-only — a `.each` mention in a comment no longer counts. The recorded-test reviewer applies the same runtime-skip ban, fail-closed unfoldable-selector rule, and positional-pick exception-comment rule as the generated path.
- Gate runs treat flaky results as failures: a test that passed only after a Playwright retry fails the executed gate ("passed on retry" is a deterministic-test failure).
- The Media Planner minimum campaign duration generated test targets `https://www.dev.rtd.js-devops.co.uk/` through `PLAYWRIGHT_TEST_BASE_URL` and requires the `chromium-auth` project.
- The Media Planner test enables local storage key `feature-flags` with `FEATURE_NECTAR_AI`, `FEATURE_NUP`, and `FEATURE_NECTAR_AI_MP` before navigating to `/planning`.
- The configured minimum duration for `DD Competition page` is `21` days in the documented dev environment. A generated test would read `E2E_MP_DD_COMPETITION_PAGE_MIN_DURATION_DAYS` (default `21`) so another non-production environment can override it. The Media Planner spec is `pending-generation`: its test is authored against the live authenticated environment and is not committed here.
- Auth-required generated specs are still validated and statically reviewed when `E2E_AUTH_ENABLED` is not true, but live Playwright execution is skipped by `ai:test:gate:all` until authenticated execution is configured.
- Existing non-committed Playwright storage state can be reused by setting `E2E_AUTH_ENABLED=true`, `E2E_AUTH_REUSE_STATE=true`, and `E2E_AUTH_STATE_PATH`.
- `agent-browser` is a pre-generation DOM/accessibility discovery tool only; Playwright Test remains the deterministic runner and the framework owns selector selection.
- DOM discovery artifacts live under `.ai-runs/dom-discovery/` and are ignored because they may contain current UI text or screenshots.
- `agent-browser.json` limits default discovery to local hosts and the current documented dev host. Add domains deliberately when a new non-production target is approved.
- CI validates the local `agent-browser` skill integration by default. Full browser install/doctor validation is opt-in because downloading Chrome for Testing can make every CI run slower and more network-sensitive.
- Generated-test review rejects persisted `agent-browser` refs such as `@e1`, requires Page Object or Component Object locator ownership, and rejects generated tests that assert in multiple steps instead of one final outcome assertion step.
- Chrome DevTools Recorder JSON files live under `recordings/*.json` and are first-class generation contracts for the recording-driven framework path.
- Recorded tests live under `tests/recorded/*.spec.ts` and use headers of the form `/* recording: <path> title:<title> sha256:<hash> */`.
- Recording validation treats `setViewport` and `scroll` as non-behavioral Recorder metadata. Device and viewport coverage should be modeled in Playwright projects rather than generated test steps. Normalization surfaces dropped metadata explicitly: `setViewport`/`scroll` steps under `ignoredSteps` and step `assertedEvents` under `ignoredEvents`, each with a reason; both channels are excluded from the sha256 behavior hash by design.
- Recording validation requires at least one `waitForElement` step so generated tests have an assertion-worthy observable outcome.
- Recording validation allows only local or explicitly approved non-production hosts. The allowed host list is derived from localhost defaults, `PLAYWRIGHT_TEST_BASE_URL`, and `agent-browser.json`.
- Chrome Recorder selectors are translated into Playwright locators where possible. Stable meaningful `data-testid` selectors are preferred first, then ARIA role/name, label/placeholder where available, and stable visible text; raw CSS is only a fallback and generated tests must include a `locator-policy:exception` comment.
- The recording hash is computed from normalized behavior, selected locators, typed values, and assertion mapping. Editing the Recorder JSON behavior requires updating generated-test headers.
- `recordings/_example.json` is a template (underscore-prefixed) and is skipped by the recording gates, mirroring `specs/_template.md`. The committed recorded test pair is `recordings/checkout-confirmation.json` -> `tests/recorded/checkout-confirmation.spec.ts`, which runs against the demo app's `/recorded-example/checkout` page.
- AI test generation selects a "brain" at run time: if `ANTHROPIC_API_KEY` or `OPENAI_API_KEY` is set, that API is used; otherwise a locally installed `claude` or `codex` CLI is used. `AI_BRAIN` forces a choice (with `claude`/`codex` accepted as aliases) and errors clearly when the forced brain is unavailable. `npm run ai:brain:doctor` reports the selection without making a paid call. No SDK dependency is added — API calls use the built-in `fetch`. `.env` at the repo root is read by the AI scripts themselves via a tiny dependency-free parser (the dotenv package is no longer used by `scripts/ai`; real environment variables always win over `.env`). REST calls pin `claude-opus-4-8` / `gpt-4o-2024-11-20` by default, send no sampling parameters to Anthropic (removed on current Opus models; determinism is enforced by the static gates instead), retry 429/5xx at most twice honoring Retry-After, and time out after `AI_BRAIN_TIMEOUT_MS` (default 120s). Truncated (`stop_reason=max_tokens` / `finish_reason=length`) or refused responses fail fast with instructions to raise `ANTHROPIC_MAX_TOKENS`/`OPENAI_MAX_TOKENS`.
- `AI_DOTENV_PATH` (settable in the real environment only) overrides the `.env` path the AI scripts read — mainly for tests/CI hermeticity. It is documented in `node scripts/ai/ai-doctor.mjs --help` and `.env.example`.
- The AI client deliberately uses raw fetch with no SDK so the framework stays dependency-free. If the project ever accepts runtime dependencies, the official SDKs (`@anthropic-ai/sdk`, `openai`) are the recommended path — they provide typed errors, automatic retries, and streaming out of the box.
- Allure reporting is enabled by default via the `allure-playwright` reporter (`ALLURE_ENABLED=false` disables it). `npm run allure:generate` builds the HTML report from `allure-results/` and requires a Java runtime on `PATH`; CI uploads it as an artifact. `allure-results/` and `allure-report/` are gitignored. AI gate scripts run Playwright with `--reporter=html,json`, so gate runs do not produce Allure results — only plain `playwright test` runs do.
- CI installs browsers per need (quality job: chromium only; regression matrix: the matrix project's engine, with `chromium-auth`/`mobile-chrome` mapping to chromium); `npm run pw:install` remains the full local install of all engines.
- `pages/HomePage.ts` and `components/Header.ts` are exercised by `tests/smoke/home.smoke.spec.ts`. The `api` fixture in `fixtures/test.ts` remains intentional starter scaffolding — the demo app exposes no GET JSON endpoint to exercise it honestly. `fixtures/data.fixture.ts` was deleted as dead code; the `testData` fixture lives solely in `fixtures/test.ts`.
- The psychicbook staging flow (`tests/staging/psychicbook-find-your-match.spec.ts`, documented in `docs/ai-testing/psychicbook-find-your-match-flow.md`) targets the live `https://user.stage.psychicbook.net` environment ONLY. It is not mirrored into the bundled demo app and is excluded from the demo-app gates and CI sweep: it runs under the opt-in `staging` Playwright project (`E2E_STAGING_ENABLED=true`, added by `playwright.config.ts`; every demo-app project `testIgnore`s `tests/staging/`). Run it with `npm run test:e2e:staging`. The test carries no spec header and is listed in `tests/.no-header-allowlist`.
- The staging host sits behind HTTP basic auth (a browser "system login" prompt, not an application flow). `playwright.config.ts` supplies `httpCredentials` only when both `E2E_HTTP_BASIC_USERNAME` and `E2E_HTTP_BASIC_PASSWORD` are set in the environment or gitignored `.env`; the credentials are never committed. The `staging` project's base URL defaults to the staging host.
- The flow was discovered live on 2026-06-11 (ARIA snapshots and screenshots under gitignored `.ai-runs/`). The staging UI exposes no `data-testid` attributes, so its Page Objects use role/name and placeholder locators; the four verification-code inputs are anonymous (`inputmode="numeric"`, `maxlength="1"`, no accessible name/label/placeholder) and require a CSS fallback plus positional digit picks, each carrying `// locator-policy:exception` comments.
- Staging authenticates returning users straight to `/psychics/` when the 4th code digit is typed (auto-submit, no Continue button, no profile step), accepts the deterministic verification code `1234` for the QA-owned test email `den.muzya@gmail.com`, and keeps the user on the "Verify your Email" screen (digit inputs outlined red, no persistent inline error text) on a wrong code. Every staging run of the flow sends a real verification email to that mailbox; resend is rate-limited (~30s) per session.
- Staging serves the authenticated home variant (the one with the "Match with advisor" find-your-match widget) only on a full document load. After an in-session login, client-side navigation to Home keeps the unauthenticated home shell, which has no match widget at all, and a hidden chat-composer input shares the match textarea's placeholder text (probe-verified with a reload A/B on 2026-06-11). `PsychicsPage.goHome()` therefore reloads the document once after clicking Home, and the match field locator is role-based (`getByRole('textbox', { name: 'Type your question here…' })`) so the hidden composer can never be matched.
- Submitting the match question triggers a "Matching you with your advisor…" modal (~10s) that resolves to a "Meet Your Psychic Match" result page; the find-your-match heading is transient, so AC-006 asserts the signals stable across the whole lifecycle — URL `/match-advisor/` plus the visible "Psychic Match" breadcrumb (exactly one element throughout). The cookie-consent banner and lazy hydration are real-environment behaviors the Page Objects dismiss/scroll past.
